Goldman-Bold is the engine's display face and is published on Google Fonts under the same name, so these artboards use the real thing. GoldmanSansCd_Rg - the body face - is not published there; the artboards substitute Barlow Semi Condensed, which is close in width and weight. Exported PNG/PDF falls back further, so treat exported type as indicative.
Sizes are ABSOLUTE pixels in the engine, not relative - which is why these artboards are drawn at 1920 x 1080 rather than a smaller frame.

Icons - a sheet of our own

The built-in sheet is game-icons.net art: solid, fantasy-flavored, and thin in the places ePADD needs it - Help is a pointing hand, Airwing an unreadable blob, and Quests a WANTED poster with text baked into the glyph. So ePADD ships its own: 512 x 512, 4 x 4 cells of 128px, white on transparent exactly like the engine sheet, so a style string's color: still does all the tinting. Source is design/epadd/sheet.html - SVG, rasterized headless, so a glyph is edited rather than redrawn.

The names are namespaced. The icon registry is one flat namespace and a registration is a CLAIM on it: a bare brain takes over the built-in glyph for everything else that draws it, and a bare cargo is one addon claiming a word every other addon might want.
Claiming them is one call - the same one a mission would use to re-skin them. Nothing that DRAWS an icon changes, which is the point of naming them: a mission can re-point cargo at its own art and every screen that draws it follows.
gui_icon_add_atlas_grid(media_shared("epadd/icons"), 4, 4, cell=128, names=[
    "epadd.cargo", "epadd.fabricate", "epadd.upgrades", "epadd.quests",
    "epadd.library", "epadd.help", "epadd.airwing", "epadd.casino",
    "epadd.damage", "epadd.hangar", "epadd.comms_log", "epadd.standings",
    "epadd.debug", "epadd.mast", "epadd.brain", "epadd.coverage"])

# thereafter an app just names one, and gui_icon_name resolves it
gui_app_register("cargo", title="Cargo", icon="epadd.cargo", consoles="engineering")

Three things to get right in the code

The strip button must carry a literal, not the route path. Today the label is the raw lowercase path ($text:{tab} at maststorypage.py:788), so a route named epadd would draw as "epadd". Phase 3 draws this button itself and must pass "ePADD".
Group order is not registration order. The existing strip iterates a dict and reverses it with add_front, which is exactly the ordering problem being fixed - the app list must sort explicitly on (group, sort, title).
Drawing still consumes the declaration. ePADD mode changes what is drawn, not the declare-every-build contract: console_tabs and __back_tab__ are still cleared at the end of the build, and the app registry is a separate, mission-scoped table.
